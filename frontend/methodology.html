🌍 Overview

The VIIRS Nightlights Analysis Tool processes satellite nighttime light data to track economic activity, urban development, and infrastructure changes over time (2012-2025). This document provides a complete end-to-end explanation of how the system works, from user input to final visualization.

Key Features

  • Real-time data fetching from NOAA Earth Observation Group
  • Automated geocoding via OpenStreetMap Nominatim
  • Scientific bias correction using Elvidge et al. (2021) methodology
  • Interactive visualization with Leaflet.js and D3.js
  • Multi-city comparison capabilities
  • Data export in Excel, CSV, and JSON formats

🔍 STEP 1: City Geocoding

When you enter a city name (e.g., "Mumbai" or "Berlin, Germany"), the system sends a request to the OpenStreetMap Nominatim API to convert the place name into precise coordinates.

How It Works

  1. API Request: System sends city name to Nominatim
  2. Response Processing: Receives lat/lon coordinates and place type
  3. Radius Determination: Assigns analysis radius based on city type
  4. Validation: Checks coordinates are within VIIRS coverage

📐 STEP 3: Spatial Aggregation & City Boundaries

⚠️ IMPORTANT: Methodology Limitation

This is the most critical section for understanding data accuracy and appropriate use cases.

How City Boundaries Are Defined

Unlike GIS software that can use actual administrative boundaries, this tool uses a simplified approach:

  1. Fixed Circular Radius: Each city is assigned a predefined radius (e.g., Mumbai: 20 km, Tiruppur: 8 km)
  2. Square Bounding Box Extraction: Despite the "radius" being circular, data is extracted from a square box
  3. Equal-Weight Averaging: All pixels within the square are averaged with equal weight

🔬 STEP 4: Bias Correction

VIIRS monthly composites are created by averaging only cloud-free observations. This tool applies the Elvidge et al. (2021) correction methodology to compensate for systematic biases introduced by cloud cover.

The Correction Formula

corrected_radiance = raw_radiance × (1 + α × (1 - cf_cvg/100))

Where:

  • raw_radiance = Average pixel value from GeoTIFF
  • α = 0.2 = Empirically determined correction coefficient
  • cf_cvg = Cloud-free coverage percentage (0-100%)

Example Corrections

Raw Radiance Cloud-Free Coverage Correction Factor Corrected Radiance
10.080%1.0410.4
10.060%1.0810.8
10.040%1.1211.2
10.020%1.1611.6

Interpretation: Lower cloud-free coverage → higher correction (more uncertain data).

Known Issues

  1. Coastal Cities: Water areas included in square extraction
  2. Linear Cities: Elongated cities (along rivers, coasts) poorly represented
  3. Industrial Corridors: Satellite industrial zones may be outside radius
  4. High Latitude: Longitude degree approximation breaks down (±50% error at 60°)
  5. No Distance Weighting: Suburban edge pixels weighted equally to urban core
  6. Administrative Boundaries: Does not follow official city limits

✅ Appropriate Use Cases

This tool is GOOD for:

  • Temporal trend analysis within cities
  • City-to-city comparative analysis
  • Economic activity monitoring
  • Regional development tracking
  • Policy impact assessment
  • Educational demonstrations

❌ Inappropriate Use Cases

This tool is NOT GOOD for:

  • Precise urban boundary mapping
  • Irregular/linear city shapes (coastal cities)
  • Fine spatial detail analysis
  • Absolute radiance accuracy comparisons
  • Dense urban core metrics
  • Distance-weighted analysis
  • Publication-grade research (without additional validation)

Usage, fair access & rate limits

This tool is hosted on a shared, capacity-limited server so that anyone can explore VIIRS nightlights without an account. To keep the service stable for many visitors, the API applies automatic limits. Defaults below can be changed by the operator via environment variables.

Per-visitor (IP) limits

  • ~60 API requests per minute per IP address (RATE_LIMIT_PER_MIN, default 60). Excess requests receive HTTP 429 with a short “retry soon” message.
  • Limits apply across search, autocomplete, and VIIRS data endpoints combined.
  • There is no user login; fairness is based on client IP (and optionally X-Forwarded-For when behind a reverse proxy).

Concurrent load on the server

  • Up to 4 simultaneous upstream operations (MAX_INFLIGHT_NETWORK, default 4) for geocoding (OpenStreetMap) and live Google Earth Engine fetches when data is not already cached.
  • If the server is saturated, new network-heavy requests may receive HTTP 503 (“Server is busy”) until capacity frees up.
  • Preloaded cities and the ~800-place hotlist usually respond from the local cache in milliseconds and do not count as network slots.

Analysis size limits (per request)

  • Up to 5 individual cities in one comparison, or one predefined cluster (e.g. Ports of China) with up to 12 places (MAX_PLACES_PER_REQUEST).
  • Clusters and single-city analyses use the same date-range and export rules as the main app.

What this means in practice

  • Normal interactive use (search, add a few cities, play the timeline) should rarely hit limits.
  • Automated scraping, load testing, or many parallel tabs may trigger 429/503 responses—please space out requests.
  • Heavy classroom or workshop use: stagger “Analyze” clicks or run a self-hosted copy from the repository.

Hosting your own instance

Operators can raise limits, add a CDN (see docs/CLOUDFLARE_CDN.md in the repo), and use the prebuilt viirs_cache_hotlist.db so most users never wait on GEE. Public demo defaults prioritize stability over unlimited throughput.
